# Управление проектом через документацию

Версия 1 · 2026-09-21. Подсистема, которая позволяет обсуждать идеи в чате с Claude, опираясь на структурированное знание о проекте, превращать их в задачи, видеть прогресс на портале Bitrix24 и не давать документации разойтись с кодом.

## 1. Принципы

1. **Документация — источник истины.** Не чат, не память агента, не Bitrix24. Если факта нет в `docs/`, его нет. Каждая область сайта описана в `docs/features/<area>.md` в двух частях: что реализовано (проверено по коду, с датой) и что запланировано (ссылки на T-ID).
2. **Два суффикса.** `<topic>.md` — справочник: как устроено, файлы, договорённости. `<topic>.tasks.md` — план и статус по теме, если тема больше одной задачи (например, `docs/features/leads-and-account.tasks.md` при разбивке T-005). Не смешивать «как есть» с «что будет».
3. **Идея → файл → задача.** Обсуждение в чате фиксируется в `docs/ideas/YYYY-MM-DD-<slug>.md` (проблема / варианты / решение / влияние). Задача в очереди ссылается на идею. Ничего не «принимается в работу» устно.
4. **Выполнил — синхронизируй.** Завершение задачи не считается завершением, пока `docs/features` не обновлён (Planned → Implemented с датой и коммитом) и ловушка, если была, не записана в `docs/HISTORY.md`.
5. **Секреты и внешние ID — только в env.** Bitrix24, Notion, Telegram: ни одного URL портала, ID группы, токена в репозитории. Всё в `.env.automation` (git-ignored; пример — `.env.automation.example`). Скрипты без env молча пропускают внешний синк.
6. **Бизнес-часть отдельно от кода.** Лиды, сделки, продажи, переписка с клиентами живут в Bitrix24 (ADR-0004, ADR-0007) и не попадают в репо. В репо — только задачи разработки/контента и их статусы.
7. **Один крон — одна строка в реестре.** `docs/ops/crons.md` — единственное место расписаний; новый скилл или скрипт регистрируется там до включения.

## 3. Жизненный цикл

```
чат (владелец + Claude)
  │  /idea: читает docs/features + strategy + decisions + HISTORY, уточняет 1–3 вопроса
  ▼
docs/ideas/YYYY-MM-DD-slug.md   status: new → discussed
  │  владелец решает в чате
  ▼
accepted (+ ADR, если меняется URL / локаль / схема / канал)   или   rejected (с причиной)
  │  /task-add: блок(и) в tasks/TASKS.md с acceptance, ice, idea:
  ▼
tasks/TASKS.md Queue            idea status: converted; строка в docs/features/<area>.md Planned
  │  node scripts/pm/b24-tasks-sync.mjs --push  (создаёт "[T-NNN] Заголовок" в проекте Bitrix24)
  ▼
Bitrix24 проект                 прогресс виден владельцу и партнёрам без чтения репо
  │  /task-run (ежедневно 09:00): ветка task/T-NNN-slug → гейты → ff-merge → Done
  ▼
/docs-sync (шаг 6 task-run)     Planned → Implemented с датой и коммитом; HISTORY при ловушке;
  │                             указатели (tasks/README, docs/README, CLAUDE.md, crons.md); known drift
  ▼
отчёт tasks/reports/YYYY-MM-DD.md → --push (done → завершена + комментарий) → Telegram
  │
  ▼
/project-checkin (еженедельно)  git ↔ TASKS.md ↔ docs/features ↔ Bitrix24 ↔ ideas ↔ ADR ↔ crons;
                                дрейф → draft-задачи docs-sync; 2–3 следующие задачи с ветками
```

Статусы задачи и их отражение в Bitrix24: `draft`/`ready` → ожидает выполнения, `in-progress` → выполняется, `blocked` → отложена + комментарий с причиной, `done` → завершена + комментарий со ссылкой на отчёт и коммит. Приоритет `high` → высокий.

## 4. Роли скиллов

| Скилл              | Когда                             | Что делает с документацией                                                                               |
| ------------------ | --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `/idea`            | владелец обсуждает идею           | читает features/strategy/decisions/HISTORY, пишет `docs/ideas/*`, ADR при необходимости, задачи, зеркало |
| `/task-add`        | «добавь задачу»                   | блок в `TASKS.md` (ice, idea), строка в Planned области, `--push`                                        |
| `/task-run`        | ежедневно, headless               | реализация; шаг 6 — `docs-sync`; шаг 8 — `--push`; отчёт с секцией Docs                                  |
| `/docs-sync`       | после каждой done-задачи; вручную | Planned → Implemented, HISTORY, указатели, ADR-проверка, known drift                                     |
| `/project-checkin` | еженедельно; вручную              | сверка всех пар, draft-задачи на дрейф, 2–3 следующих задачи, отчёт, Telegram                            |
| `/seo-research`    | еженедельно                       | ресёрч → draft-задачи (`source: seo-research`); Planned в `marketing-ops.md` / `catalog.md`              |

Полный реестр с входами/выходами: [.claude/skills/README.md](../../.claude/skills/README.md).

## 5. Что лежит в env

`.env.automation` (пример в `.env.automation.example`):

| Ключ                 | Кто читает                      | Назначение                                                   |
| -------------------- | ------------------------------- | ------------------------------------------------------------ |
| `TELEGRAM_BOT_TOKEN` | `scripts/telegram-notify.mjs`   | отчёты раннера и check-in                                    |
| `TELEGRAM_CHAT_ID`   | `scripts/telegram-notify.mjs`   |                                                              |
| `B24_WEBHOOK_URL`    | `scripts/pm/b24-tasks-sync.mjs` | входящий вебхук со scope `task`, база `…/rest/<id>/<token>/` |
| `B24_TASKS_GROUP_ID` | `scripts/pm/b24-tasks-sync.mjs` | проект (рабочая группа) с задачами                           |
| `B24_RESPONSIBLE_ID` | `scripts/pm/b24-tasks-sync.mjs` | ответственный на создаваемых задачах                         |

Будущие ключи (лиды → B24 `crm.item.add`, T-005d; Notion, если понадобится экспорт) добавляются сюда же, в реестр — строка в этой таблице. В коде и документации ключи упоминаются только по имени.

## 6. Что владелец видит в Bitrix24

Проект с задачами `[T-NNN] Заголовок`, описание = блок из `TASKS.md` (описание + Acceptance), статус и приоритет синхронизированы, комментарии с причиной блокировки и ссылкой на отчёт/коммит при закрытии. Редактировать задачи на портале не нужно — следующий `--push` вернёт состояние из репо (источник истины — `TASKS.md`). Если задача закрыта вне раннера: `node scripts/pm/b24-tasks-sync.mjs --close T-NNN --comment <файл>` и статус `done` в `TASKS.md` руками.

Лиды в тот же портал — отдельная ветка (ADR-0004, T-005d), тот же принцип «ключи в env».

## 7. Веб-версия базы знаний (позже)

Варианты, когда `docs/` захочется читать не из репозитория:

| Вариант                                                                                                      | Плюсы                                                                                                                   | Минусы                                                                                                   |
| ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **A. Статический экспорт `docs/`** (VitePress / Docusaurus / Astro Starlight в `apps/docs`, деплой на Pages) | markdown как есть, ноль двойного ведения, поиск из коробки, диффы в git, приватность через basic-auth/Cloudflare Access | ещё один пакет в монорепо; не редактируется из браузера                                                  |
| B. Коллекция `docs` в Payload                                                                                | редактирование в админке, права, единый хостинг                                                                         | markdown ↔ Lexical двойное ведение или ломкая синхронизация; доки перестают быть источником истины в git |
| C. Экспорт в Notion (Notion MCP / API)                                                                       | привычный интерфейс, комментарии, шаринг                                                                                | односторонний экспорт, дрейф, ещё один секрет, зависимость от внешнего сервиса                           |

**Рекомендация: A.** Источник истины остаётся в git, публикация — сборка по коммиту в `main`. Делать после того, как `docs/features` продержится в актуальном состоянии 4+ недели (иначе публикуем дрейф). Сейчас не строим; оформить как идею `docs/ideas/…-docs-site.md`, когда появится читатель кроме владельца.

## 8. Известный дрейф

Живёт в `.claude/skills/project-checkin/SKILL.md` § «Known drift», чтобы быть рядом с проверкой. Правило: обнаружил расхождение, которое не чинишь сейчас — добавь строку; починил — удали.
