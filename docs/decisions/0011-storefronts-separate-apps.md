# ADR-0011: Витрины на одном бэкенде — простой путь к отдельным приложениям (вариант B)

**Статус:** accepted · 2026-10-06 (владелец: «b или типа того», затем «это круто, но надо, чтобы не очень сложно»)

## Context

Витрин три: `divan.group` — широкий магазин для дома, `divan.boutique` — премиум, ограниченный ассортимент при полном наборе функций, и молодёжная витрина (домена пока нет). Бэкенд один. Позже сайты могут форкаться «с другой мордой» или создаваться скриптом-скелетом. Требование «SEO first».

Варианты разобраны в [идее](../ideas/2026-10-05-two-storefronts-design-fork.md) и отчётах [option-b](../../research/tech/2026-10-05/option-b.md), [option-c](../../research/tech/2026-10-05/option-c.md). Прототипы показали, что все три витрины — один и тот же набор компонентов в разных темах (`design/concepts/`): различаются направление, палитра, режим и форма, а не структура страниц.

## Decision

**Цель — вариант B** (у витрины может быть своё приложение), **исполнение — самое простое**, в два шага:

1. **Сейчас: одно приложение, несколько доменов.** Хост → документ коллекции `storefronts` → набор темы и ассортимент. Один деплой, одна админка, одна база. Ветвление лица — через тему (T-052) и, где нужно, свои `widgets` / `pages` для витрины.
2. **Потом, только если структура витрины разойдётся** (свой чекаут, свои разделы, другой стек): вынести её в отдельное приложение `apps/<storefront>` над общим пакетом `@workspace/cms`. Код с самого начала раскладываем так, чтобы этот шаг был механическим: движок (`shared`, `entities`, `features`, Payload-конфиг) не знает про конкретную витрину.

**Наборы витрин (решение владельца 2026-10-06):**

| Витрина                      | Направление | Палитра | Режим   | Формы       |
| ---------------------------- | ----------- | ------- | ------- | ----------- |
| divan.group                  | Галерея     | Эспарто | авто    | скруглённые |
| divan.boutique               | Кино        | Гранат  | светлая | строгие     |
| молодёжная (домен не выбран) | Неон        | Лайм    | тёмная  | скруглённые |

**Товар на нескольких витринах.** В админке у товара галочки «Показывать на: divan.group / divan.boutique / молодёжная» и выбор **основной витрины** (по умолчанию первая отмеченная). Купить можно на любой отмеченной витрине. Для SEO индексируется только страница на основной витрине: на остальных — `rel=canonical` на основную и исключение из их sitemap. Свой текст описания на витрину — по желанию; если он уникален, каноникал можно снять осознанно.

**Остальное:** схема в проде меняется только миграциями (без push); медиа — в объектном хранилище; sitemap, robots, canonical, hreflang, OG и JSON-LD Organization — по хосту; ревалидация кэша с учётом хоста.

## Consequences

- Сначала фундамент, полезный и для одной витрины: ISR вместо `force-dynamic` (T-053), миграции, коллекция `storefronts` с наборами темы, галочки витрин и основная витрина у товара (T-054), система тем (T-052).
- Отдельное приложение появляется только по необходимости; до этого — один Docker-образ и один деплой в Dokploy с несколькими доменами.
- Скрипт-скелет новых сайтов позже — из шаблона витрины в этом репозитории, а не мёрджами форков.

## Уточнение 2026-10-06: как исполнен шаг 1

Владелец выбрал монорепо («монорепа — супер», «пакеты ui | темы»). Шаг 1 исполнен как **один код, отдельная сборка на витрину**, а не «один деплой, витрина по хосту в рантайме». Это уточнение заменяет слова «один Docker-образ и один деплой» в Consequences.

- `NEXT_PUBLIC_STOREFRONT=group|boutique|youth` при сборке выбирает набор темы и шрифты. В Dokploy три приложения из одного репозитория, у каждого свой `NEXT_PUBLIC_SERVER_URL`, а `DATABASE_URL` общий. Админка и база одни.
- Почему сборка, а не хост:
  1. `next/font` предзагружает только шрифты своей витрины.
  2. Атрибуты темы ставятся на `<html>` без `headers()` в layout, поэтому страницы могут остаться статическими (ISR, T-053).
  3. Свой `NEXT_PUBLIC_SERVER_URL` даёт canonical, hreflang, sitemap и robots по домену без доработок.
- Пакеты: `@workspace/ui` (примитивы, композиты, контракт токенов) | `@workspace/themes` (направления, палитры, формы, наборы витрин, проверка контраста). Отдельное `apps/<витрина>` — по-прежнему только при расхождении структуры.
- Коллекция `storefronts` для выбора темы не нужна. Ассортимент по витринам, основная витрина товара и canonical на неё остаются в T-054.
- До T-054 индексируется только `group`: остальные витрины показывают тот же каталог, поэтому `noindex`, пустой sitemap (`STOREFRONT_INDEXED` в `modules/shared/config/storefront.ts`).
