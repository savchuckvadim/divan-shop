# ADR-0011: Две витрины — отдельные приложения над общим бэкендом (вариант B)

**Статус:** accepted · 2026-10-06 (решение владельца: «b или типа того»; детали — в T-054)

## Context

Владелец планирует две витрины: `divan.group` — широкий магазин «для дома», бутик на `.boutique` — ограниченный ассортимент, премиум, полный набор функций. Бэкенд один. Позже сайты могут форкаться «с другой мордой» или создаваться скриптом-скелетом. Требование «SEO first».

Разобраны три варианта ([идея](../ideas/2026-10-05-two-storefronts-design-fork.md)): A — одно приложение на два хоста; B — монорепо, по Next-приложению на витрину над общим пакетом CMS ([отчёт](../../research/tech/2026-10-05/option-b.md)); C — ядро и отдельные репозитории витрин ([отчёт](../../research/tech/2026-10-05/option-c.md)). Владелец выбрал B: у каждой витрины своё лицо и свой бюджет JS, а класс SEO-ошибок «хост отдаёт чужие данные» исключён конструктивно.

## Decision

- Монорепо остаётся. Витрины — отдельные Next-приложения (`apps/group`, `apps/boutique`) с одним Payload-конфигом из общего пакета (`@workspace/cms`: коллекции, хуки, доступы, плагины, миграции, сгенерированные типы) и одной базой PostgreSQL.
- Админка, фоновые задачи и платёжные вебхуки — в одном приложении (`apps/group`); второе приложение читает через Local API ту же базу.
- Общие FSD-слои без привязки к лицу (`shared`, `entities`, `features`) уходят в пакеты; `widgets` и `pages` у каждой витрины свои.
- У каждого товара, проекта и статьи ровно одна домашняя витрина, где его страница индексируется; на второй витрине — тизер со ссылкой, без дубля.
- Схема в проде меняется только миграциями (expand / contract), без push; медиа — в объектном хранилище; ревалидация кэша — через эндпоинт каждого приложения, потому что `revalidateTag` действует только в своём процессе.
- Дизайн: бутик — направление «Кино», палитра «Вольфрам» (бежевый, белый, золотой); магазин — та же система тем (T-052), направление выберет владелец.

## Consequences

- Две сборки и два деплоя в Dokploy; сборки по очереди, образ без БД (ловушка в `docs/HISTORY.md`).
- Сначала фундамент, полезный и для одной витрины: ISR вместо `force-dynamic` (T-053), миграции вместо push, модель витрин и домашняя витрина документа (T-054), система тем (T-052). Второе приложение появляется, когда у бутика есть свой контент.
- Скрипт-скелет новых сайтов позже — из шаблона витрины в этом же репозитории (идея варианта C), а не мёрджами форков.
